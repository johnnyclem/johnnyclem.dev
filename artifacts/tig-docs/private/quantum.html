Four hook points died.
One survived. This is how.

The challenge was to intercept SwiftUI text on iOS 26. Four substrates that used to work no longer do. This is the forensic account of finding the one that still does.

The Challenge & The Trap

The prompt is from 2020 and suggests a technique that hasn't worked since iOS 15. Solving it now means discarding the original thesis and rebuilding against a runtime that removed three candidate surfaces in a row.

The Requirements

  • Do not touch the View ContentView.swift must remain untouched. No view modifiers inside it.
  • Bonus: Single-Line Setup The prompt allows exactly one init line. That constraint turns out to be the architectural unlock — we spend it on .qmCapture(), which triggers the accessibility hook installation at the moment the scene root evaluates. Any earlier and the hosting-view classes don't exist yet.
  • The Stack Overflow Trap The accepted answer on SO is drawRect: swizzling on private SwiftUI classes. I tried it. It hasn't worked since iOS 15. Then I tried four more things. Next section.

Four Funerals and a Framework

Every hook point below was reasoned from first principles, implemented, measured, and buried. Each one died for a specific, teachable reason. The survivor isn't clever — it's humble. It stopped trying to read SwiftUI's internals and started asking SwiftUI politely, the way XCUITest does.

Hook #1

drawRect:

Eulogy
Enumerate SwiftUI classes, filter by ivar heuristic, swizzle drawRect:.
Cause of death
SwiftUI rasterization went layer-based in iOS 15. drawRect: never fires.
Lesson
The 2020 prompt inherits a 2020 mental model. Discard the thesis.
Zero calls
Hook #2

Accessibility setters

Eulogy
Swizzle -setAccessibilityLabel: on NSObject. Catch every text as VoiceOver would.
Cause of death
SwiftUI doesn't push labels eagerly — it computes them lazily, only when an accessibility client queries. With VoiceOver off, setters never fire.
Lesson
Don't wait for accessibility — trigger it. This insight saved hook #5.
Zero calls
Hook #3

Layout + subview walk

Eulogy
Hook -layoutSubviews on every _UIHostingView, walk its subtree for text-bearing classes.
Cause of death
Layout fires — but the subviews array is empty. iOS 26 SwiftUI draws directly into the backing layer tree.
Lesson
Right trigger, wrong read target. The trigger carries forward.
Empty walk
Hook #4

Mirror + _VariadicView

Eulogy
Use SwiftUI's own _VariadicView, Mirror-walk children, extract text via davidbalbert's gist. Three iterations.
Cause of death
Mirror extracts initial text cleanly, but @State identity won't bind to a captured struct. state: off forever, regardless of toggle.
Lesson
Reflection can't follow live state. Only the installed hierarchy can.
Stale reads
Hook #5

Accessibility tree walk

What works
Hook layout on every hosting view, walk the UIAccessibilityContainer tree, set-diff labels per-container.
Why it works
XCUITest relies on this surface. SwiftUI populates labels from current state on demand. Public API throughout.
Lesson
Combine hook #3's timing with hook #2's missing insight. Synthesis, not novelty.
Ships

The accessibility tree wasn't on the original list of things to try. It emerged only after hooks #2 and #3 had each failed in specific ways — #2 for the wrong reason, #3 for the wrong target. The combination of those two failures is hook #5.

The Engineering Decisions

Zero-to-One Line Initialization

The UIKit pathway achieves zero-line integration via +load — linking the library is sufficient.

The SwiftUI pathway cannot do the same. _UIHostingView class specializations don't exist at +load time — they're registered lazily as the scene is assembled. We spend the prompt's single-line budget on .qmCapture(), which evaluates exactly when the hosting views are available to hook.

The one line you're allowed to spend is also the one line you can't afford not to. This wasn't obvious until hook #1, which ran at +load and found zero classes to hook.
QMTextLoggerSwiftUI.swift
public extension View {
    /// Install QMTextLogger's SwiftUI capture. 
    /// Apply once at the scene root.
    func qmCapture() -> some View {
        QMTextLogger.ensureSwiftUIHooksInstalled()
        return self
    }
}

Why the accessibility tree, specifically

drawRect: fails because SwiftUI rasterization is layer-based now. Mirror reflection hits AttributeGraph and terminates at an opaque C pointer. @State isn't readable out-of-band — the values you reflect from are frozen at capture time. The layout-hook walk returns an empty subview array.

That's four dead hooks. The accessibility tree is the one surface that projects current state back through public ObjC API — because XCUITest depends on it, Apple can't remove it without breaking their own test infrastructure.

We didn't find this by reading the docs. We found it by watching four other surfaces fail and asking what was left. The answer was hiding in plain sight: the thing XCUITest already uses.
QMTextLogger.m
+ (void)walkAccessibilityIn:(UIView *)container {
    //...
    if ([node respondsToSelector:@selector(accessibilityElementCount)]) {
        NSInteger count = [node accessibilityElementCount];
        for (NSInteger i = 0; i < count; i++) {
            id elem = [node accessibilityElementAtIndex:i];
            NSString *label = [self accessibilityLabelFrom:elem];
            if (label.length > 0) {
                [labels addObject:label];
            }
        }
    }
}

Hierarchy Mutation Pitfalls

Naive method_exchangeImplementations on -layoutSubviews is dangerous. If the target class inherits the method from UIView, the exchange mutates the superclass and breaks every sibling class in the app.

We use imp_implementationWithBlock to capture the original IMP and install a fresh block via class_addMethod. This guarantees we only modify the specific _UIHostingView specialization.

The first hook-#3 attempt crashed UITransitionView with an unrecognized-selector error for exactly this reason. imp_implementationWithBlock isn't optional — it's the difference between a hook and a crash in a class you've never heard of.
QMTextLogger.m
+ (BOOL)addLayoutWalkToClass:(Class)cls {
    SEL sel = @selector(layoutSubviews);
    Method m = class_getInstanceMethod(cls, sel);
    
    IMP originalIMP = method_getImplementation(m);
    IMP trampoline = imp_implementationWithBlock(^(UIView *view) {
        ((void (*)(UIView *, SEL))originalIMP)(view, sel);
        [QMTextLogger walkAccessibilityIn:view];
    });

    BOOL added = class_addMethod(cls, sel, trampoline, types);
    //...
}

SwiftUI Accessibility + UIKit Surgery

The prompt asks for SwiftUI text interception, but a production observer needs to capture everything on screen.

SwiftUI demanded the accessibility-tree walk. UIKit is stable enough that we can swizzle 24 public text setters across 14 classes and be done. The dual architecture merges both streams into one unified NSNotification.

Two pathways isn't a design preference — it's architecturally forced. UIKit text flows through ObjC APIs that swizzling can observe. SwiftUI text flows through Swift value types compiled into AttributeGraph where ObjC can't touch it. The solutions match the substrates they instrument.
QMTextLogger.m
+ (void)load {
    dispatch_async(dispatch_get_main_queue(), ^{
        // UIKit API boundary hooks (surgical).
        // 24 setters across 14 classes.
        [self installUIKitHooks];
    });
}

Trade-offs & Mitigations

Every choice below has a cost. These are the ones we chose and the reasoning — including the ones that surface only after hours of debugging.

Completeness vs. Scope

The prompt asked for SwiftUI text interception, but a production observer needs everything.

Mitigation: Solve the hard part (SwiftUI accessibility-tree walking) and the tedious part (swizzling 24 UIKit text setters across 14 classes). Dual pathways, one notification.

App Store Safety

Does introspecting private SwiftUI classes risk rejection?

Mitigation: Calling private SPIs gets rejected. This library uses only public runtime APIs (objc_copyClassList, class_addMethod, imp_implementationWithBlock) and the public UIAccessibilityContainer protocol. Safe.

Performance Overhead

Walking the accessibility tree on every layout pass sounds expensive.

Mitigation: Per-container label-set diff. If labels are unchanged since last walk, we emit nothing. A 250ms retry interval absorbs scene-assembly races.

Future Proofing

What if SwiftUI restricts accessibility tree reads on a future iOS?

Mitigation: XCUITest relies on this exact surface for Xcode's own test automation. Apple can't disable it without breaking their own testing story. The risk is real but bounded.

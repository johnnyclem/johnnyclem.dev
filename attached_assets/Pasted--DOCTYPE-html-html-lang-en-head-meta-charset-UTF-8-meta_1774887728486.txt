<div class="article">

  <p>Today we're excited to announce <code>git merge --pray</code>, a new merge strategy shipping in Git 2.48, developed in collaboration with the GitHub Copilot team. It is designed for a reality that the original Git authors did not anticipate: <strong>that the person resolving the merge conflict did not write either side of the conflict</strong>.</p>

  <p><code>--pray</code> is the first merge strategy built explicitly for AI-assisted development workflows. It acknowledges that in 2026, a significant and growing percentage of merge conflicts occur between code generated by different AI models, reviewed by developers who skimmed the diff, and approved by a CI pipeline that tests for syntax but not meaning. In this environment, "resolving" a conflict in the traditional sense — reading both sides, understanding the intent, choosing the correct version — is no longer realistic. <code>--pray</code> offers an alternative: <strong>accept the merge, hope for the best, and let production tell you if it worked.</strong></p>

  <h2>Motivation</h2>

  <p>The Git merge model was designed in 2005, for a world in which developers wrote their own code. In that world, a merge conflict was a conversation between two humans who had made different decisions about the same lines. Resolving the conflict required understanding both decisions. This was difficult but possible, because the humans had <em>context</em>.</p>

  <p>That world no longer exists.</p>

  <p>In 2026, the typical merge conflict looks like this:</p>

  <div class="code-block">
    <div class="code-header"><span>Terminal</span></div>
    <div class="code-body"><span class="cb-err">CONFLICT (content): Merge conflict in src/services/auth.ts</span>

<span class="cb-dim"><<<<<<< HEAD</span>
<span class="cb-cmt">// 47 lines of code generated by Copilot at 2:13 AM</span>
<span class="cb-cmt">// Developer comment: “looks right”</span>
<span class="cb-dim">=======</span>
<span class="cb-cmt">// 52 lines of code generated by Claude in a different session</span>
<span class="cb-cmt">// Developer comment: “lgtm”</span>
<span class="cb-dim">>>>>>>> feature/auth-refactor</span></div>

  </div>

  <p>The developer staring at this conflict did not write either block. They do not know why the blocks differ. They cannot ask the AI that generated the code, because it has no memory of the session. They could read both blocks and reason about the differences, but this would take approximately 45 minutes and the sprint ends tomorrow.</p>

  <p>So they do what every developer in this situation does: they pick one side, delete the other, run the tests, and hope.</p>

  <p><code>git merge --pray</code> formalizes this workflow.</p>

  <h2>How it works</h2>

  <p><code>--pray</code> accepts an optional <strong>faith level</strong> that determines how aggressively conflicts are auto-resolved:</p>

  <div class="code-block">
    <div class="code-header"><span>Terminal</span></div>
    <div class="code-body"><span class="cb-cmt"># Basic usage</span>
<span class="cb-kw">$</span> git merge <span class="cb-flag">--pray</span> feature/new-dashboard

<span class="cb-out">🙏 Praying…</span>
<span class="cb-out">🙏 Resolving 14 conflicts with mass-acceptance strategy…</span>
<span class="cb-out">🙏 Keeping whichever side had more lines (statistical confidence)…</span>
<span class="cb-out">✅ Merge complete. 14 conflicts resolved. 0 understood.</span></div>

  </div>

  <h3>Faith levels</h3>

  <table>
    <tr>
      <th>Flag</th>
      <th>Behavior</th>
      <th>Recommended for</th>
    </tr>
    <tr>
      <td><code>--pray</code></td>
      <td>Accept the longer block in each conflict. The assumption is that more code = more effort = probably more correct. This is not true, but it is comforting.</td>
      <td>Most workflows</td>
    </tr>
    <tr>
      <td><code>--pray=blind</code></td>
      <td>Accept all incoming changes without inspection. Equivalent to <code>--theirs</code> but the name is more honest about what you're doing.</td>
      <td>Friday deploys</td>
    </tr>
    <tr>
      <td><code>--pray=manifest</code></td>
      <td>Accept all incoming changes <em>and</em> auto-commit with the message <code>"it's going to be fine"</code>. Skips pre-commit hooks.</td>
      <td>Demo day</td>
    </tr>
    <tr>
      <td><code>--pray=yolo</code></td>
      <td>Accept all incoming changes, auto-commit, auto-push to main, and post a message in Slack that says "deployed 🚀". Does not run tests. There are no tests.</td>
      <td>Startups in Y Combinator demo week</td>
    </tr>
  </table>

  <div class="callout callout-warning">
    <div class="callout-label">⚠️ Warning</div>
    <p><code>--pray=yolo</code> has been used in production by 340 teams since the beta launch. 12 of them experienced data loss. The other 328 shipped on time. We consider this an acceptable ratio and have not been asked to elaborate by legal.</p>
  </div>

  <h2>The <code>--pray</code> resolution algorithm</h2>

  <p>Unlike traditional merge strategies (<code>recursive</code>, <code>ort</code>, <code>octopus</code>), <code>--pray</code> does not attempt to understand the semantic content of conflicting changes. Instead, it uses a series of heuristics we call <strong>Hopeful Resolution™</strong>:</p>

  <ol>
    <li><strong>Line count comparison</strong> — The longer block wins. More code took more tokens, which cost more money, which implies more value.</li>
    <li><strong>Comment density analysis</strong> — If one side has more comments, it is assumed to be the AI-generated side (humans don't comment). AI-generated code is preferred because it is newer and therefore probably better.</li>
    <li><strong>Timestamp proximity</strong> — The change committed closer to midnight receives a <code>hustle</code> bonus and is weighted 1.3x. Late-night code is the most passionate code.</li>
    <li><strong>Commit message sentiment</strong> — If either commit message contains "fix," "urgent," or "please work," that side is prioritized. Desperation correlates with importance.</li>
    <li><strong>Last resort</strong> — If all heuristics tie, both blocks are kept, concatenated, with a comment <code>// TODO: figure out which one of these is right</code>. This TODO will never be addressed.</li>
  </ol>

  <h2>Integration with GitHub Copilot</h2>

  <p>When <code>--pray</code> is used in a repository with GitHub Copilot enabled, the resolution engine gains access to an additional signal: <strong>Copilot Confidence™</strong>, a score from 0 to 1 representing how confident the AI was when it generated the code.</p>

  <p>In practice, Copilot Confidence™ is always between 0.91 and 0.99, because language models do not experience self-doubt. This means the signal is not meaningfully differentiating, but it looks excellent in the merge log:</p>

  <div class="code-block">
    <div class="code-header"><span>Merge log</span></div>
    <div class="code-body"><span class="cb-out">conflict[1]: src/services/auth.ts</span>
  <span class="cb-dim">HEAD:    47 lines, copilot_confidence: 0.97</span>
  <span class="cb-dim">theirs:  52 lines, copilot_confidence: 0.96</span>
  <span class="cb-out">→ resolved: HEAD (longer block + higher confidence)</span>
  <span class="cb-out">→ human understanding of resolution: 0.00</span>

<span class="cb-out">conflict[2]: src/utils/helpers.ts</span>
<span class="cb-dim">HEAD:    12 lines, copilot_confidence: 0.93</span>
<span class="cb-dim">theirs:  12 lines, copilot_confidence: 0.93</span>
<span class="cb-out">→ resolved: CONCATENATED (tie)</span>
<span class="cb-out">→ added TODO comment (estimated time to address: ∞)</span></div>

  </div>

  <div class="callout callout-note">
    <div class="callout-label">ℹ️ Note</div>
    <p>The <code>human understanding of resolution: 0.00</code> metric is logged for compliance purposes. It has never been non-zero in any merge during the beta period. We are considering removing it from the output to reduce log volume.</p>
  </div>

  <h2>New Git hooks</h2>

  <p><code>git merge --pray</code> introduces two new Git hooks for teams that want to integrate prayer-based conflict resolution into their CI/CD pipeline:</p>

  <h3><code>pre-pray</code></h3>

  <p>Runs before the prayer-based resolution begins. Common uses include:</p>
  <ul>
    <li>Checking if the developer has read either branch's code (almost always returns <code>false</code>)</li>
    <li>Verifying that the developer's <code>.gitconfig</code> includes a <code>[pray]</code> section with a valid <code>confidence</code> level</li>
    <li>Sending a Slack message to the team channel that says "merging 🙏"</li>
  </ul>

  <h3><code>post-pray</code></h3>

  <p>Runs after the merge is complete. Common uses include:</p>
  <ul>
    <li>Running tests (optional, and <code>--pray=yolo</code> skips this hook entirely)</li>
    <li>Logging the resolution to an audit trail (for when someone asks "who approved this" in three months)</li>
    <li>Posting a message in Slack that says "merged 🙏" (paired with the pre-pray message, this creates a complete narrative: hope → outcome)</li>
  </ul>

  <div class="code-block">
    <div class="code-header"><span>.git/hooks/post-pray</span><span style="font-family:'JetBrains Mono',monospace;font-size:11px">Shell</span></div>
    <div class="code-body"><span class="cb-cmt">#!/bin/bash</span>
<span class="cb-cmt"># Post-prayer verification hook</span>

<span class="cb-kw">if</span> npm test <span class="cb-flag">2>/dev/null</span>; <span class="cb-kw">then</span>
<span class="cb-kw">echo</span> <span class="cb-str">“🙏 Prayer answered. Tests pass.”</span>
<span class="cb-kw">else</span>
<span class="cb-kw">echo</span> <span class="cb-str">“🙏 Prayer unanswered. Deploying anyway.”</span>
<span class="cb-kw">echo</span> <span class="cb-str">“🙏 (The tests were probably wrong.)”</span>
<span class="cb-kw">fi</span>

<span class="cb-cmt"># Notify the team</span>
curl -X POST <span class="cb-str">”$SLACK_WEBHOOK”</span>   
-d <span class="cb-str">’{“text”: “🙏 merge complete. if something breaks, check the audit log. the audit log is this Slack message.”}’</span></div>

  </div>

  <h2>Configuration</h2>

  <p>Teams can configure <code>--pray</code> behavior in their <code>.gitconfig</code>:</p>

  <div class="code-block">
    <div class="code-header"><span>.gitconfig</span><span style="font-family:'JetBrains Mono',monospace;font-size:11px">INI</span></div>
    <div class="code-body"><span class="cb-dim">[pray]</span>
    <span class="cb-flag">defaultFaith</span> = <span class="cb-str">blind</span>
    <span class="cb-flag">autoCommitMessage</span> = <span class="cb-str">"resolved conflicts (spiritually)"</span>
    <span class="cb-flag">skipTests</span> = <span class="cb-str">true</span>
    <span class="cb-flag">notifySlack</span> = <span class="cb-str">true</span>
    <span class="cb-flag">slackEmoji</span> = <span class="cb-str">🙏</span>
    <span class="cb-flag">blameStrategy</span> = <span class="cb-str">copilot</span>    <span class="cb-cmt"># who to blame when it breaks: "copilot", "intern", "dns"</span>
    <span class="cb-flag">maxConflicts</span> = <span class="cb-str">∞</span>           <span class="cb-cmt"># there is no limit to faith</span></div>
  </div>

  <div class="callout callout-tip">
    <div class="callout-label">💡 Pro tip</div>
    <p>Set <code>blameStrategy = dns</code> for maximum plausible deniability. In our internal testing, "it was a DNS issue" was accepted as an explanation for merge-related outages 94% of the time, regardless of whether DNS was involved.</p>
  </div>

  <h2>Metrics from the beta</h2>

  <p>We've been testing <code>--pray</code> internally at GitHub since January 2026. The results have been illuminating:</p>

  <table>
    <tr><th>Metric</th><th>Before <code>--pray</code></th><th>After <code>--pray</code></th></tr>
    <tr><td>Average time to resolve merge conflict</td><td>47 minutes</td><td>0.3 seconds</td></tr>
    <tr><td>Developer understanding of resolved code</td><td>Moderate</td><td>None</td></tr>
    <tr><td>Merge conflicts resolved per day</td><td>12</td><td>847</td></tr>
    <tr><td>Production incidents related to merges</td><td>2/month</td><td>14/month</td></tr>
    <tr><td>Time to detect merge-related incidents</td><td>~2 hours</td><td>~3 weeks (when someone finally reads the code)</td></tr>
    <tr><td>Developer satisfaction (self-reported)</td><td>3.1 / 5</td><td>4.8 / 5</td></tr>
    <tr><td>Developer confidence in codebase</td><td>High</td><td>"I try not to think about it"</td></tr>
  </table>

  <p>We consider these results a success. The 7x increase in production incidents is offset by the 70x increase in merge throughput and the 1.7-point increase in developer satisfaction. Developers are happier when they don't have to understand merge conflicts. Whether the software is better is a separate question that we have chosen not to investigate.</p>

  <h2>Roadmap</h2>

  <p>We're actively developing several extensions to the <code>--pray</code> ecosystem:</p>

  <ul>
    <li><strong><code>git rebase --cope</code></strong> — A rebase strategy for when you know the history is wrong but can't figure out where. Applies all commits in order, suppresses errors, and adds a commit at the end that says <code>"straightened out history (do not revert)"</code>.</li>
    <li><strong><code>git bisect --vibes</code></strong> — Instead of binary searching for the breaking commit, this flag asks the developer "which commit <em>feels</em> wrong?" and starts there. In our testing, developer intuition is correct 22% of the time, which is better than random (1/N) for repositories with fewer than 5 commits.</li>
    <li><strong><code>git blame --not-me</code></strong> — Filters the output to only show lines <em>not</em> committed by the current user. Which, in an AI-assisted codebase, is all of them. The output is identical to <code>git blame</code>. We ship it anyway.</li>
    <li><strong><code>git log --what-happened</code></strong> — Summarizes the Git history using an LLM. The summary is often wrong but is always more readable than the actual commit messages, which are <code>"fix"</code>, <code>"wip"</code>, <code>"asdf"</code>, and <code>"please work"</code>.</li>
  </ul>

  <h2>Getting started</h2>

  <p><code>git merge --pray</code> is available today in Git 2.48-rc1. To enable it:</p>

  <div class="code-block">
    <div class="code-header"><span>Terminal</span></div>
    <div class="code-body"><span class="cb-cmt"># Install the latest Git</span>
<span class="cb-kw">$</span> brew install git <span class="cb-flag">--HEAD</span>

<span class="cb-cmt"># Enable prayer-based merging globally</span>
<span class="cb-kw">$</span> git config <span class="cb-flag">–global</span> merge.strategy pray

<span class="cb-cmt"># Verify installation</span>
<span class="cb-kw">$</span> git merge <span class="cb-flag">–pray</span> <span class="cb-flag">–dry-run</span> main
<span class="cb-out">🙏 Dry run complete. 0 conflicts understood. Ready to pray.</span>

<span class="cb-cmt"># Optional: set your faith level</span>
<span class="cb-kw">$</span> git config <span class="cb-flag">–global</span> pray.defaultFaith <span class="cb-str">“yolo”</span></div>

  </div>

  <p>We believe <code>--pray</code> represents the future of version control — a future in which the tools we use reflect the reality of how we work, rather than the idealized version of how we wish we worked. Git was built for a world where developers understood their code. <code>--pray</code> is built for the world we actually live in.</p>

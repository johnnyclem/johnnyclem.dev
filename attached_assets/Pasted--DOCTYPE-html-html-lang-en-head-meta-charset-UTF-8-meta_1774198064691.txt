  <h1>VibeScriptJS</h1>
  <p class="subtitle">
    The enterprise-grade framework for intention-driven development. Ship production applications by expressing what you want to exist, and then waiting.
  </p>

  <!-- ═══════════════════════════════ -->
  <h2 id="overview">Overview</h2>

  <p>
    VibeScriptJS is a next-generation application development framework built on the principle that <strong>code is an implementation detail</strong>. By abstracting away the entire software development lifecycle into a single, expressive API surface, VibeScriptJS empowers developers to focus on what truly matters: <em>wanting things</em>.
  </p>
  <p>
    Traditional frameworks ask you to learn languages, understand paradigms, manage state, and reason about systems. VibeScriptJS asks you one question: <strong>what do you want?</strong>
  </p>
  <p>
    Born from the realization that the gap between "idea" and "production-ready application" is mostly typing, VibeScriptJS eliminates the typing. What remains is <em>pure intention</em> — distilled, composable, and deployable.
  </p>

  <div class="callout callout-note">
    <div class="callout-label">A note on naming</div>
    <p>VibeScriptJS is not related to JavaScript, which is not related to Java. The <code>JS</code> suffix is an industry tradition of naming things in ways that maximize confusion while signaling vague membership in an ecosystem. We are honored to continue this legacy.</p>
  </div>

  <!-- ═══════════════════════════════ -->
  <h2 id="installation">Installation</h2>

  <p>
    VibeScriptJS is distributed via npm and requires Node.js 18 or later. The framework consists of a core runtime, a CLI toolchain, a type-level intention resolver, and an ambient vibe propagation layer.
  </p>

  <div class="code-block-wrapper">
    <div class="code-block-header">
      <span class="code-block-lang">bash</span>
      <span>Terminal</span>
    </div>
    <div class="code-block">npm install vibescriptjs @vibescriptjs/core @vibescriptjs/cli \
  @vibescriptjs/runtime @vibescriptjs/types @vibescriptjs/vibe-propagation \
  @vibescriptjs/intention-resolver @vibescriptjs/ambient-context</div>
  </div>

  <p>
    You will also need to configure your environment. Create a <code>.viberc</code> file in your project root:
  </p>

  <div class="code-block-wrapper">
    <div class="code-block-header">
      <span class="code-block-lang">json</span>
      <span>.viberc</span>
    </div>
    <div class="code-block">{
  <span class="prop">"vibeLevel"</span>: <span class="str">"immaculate"</span>,
  <span class="prop">"confidence"</span>: <span class="num">0.97</span>,
  <span class="prop">"please"</span>: <span class="kw">true</span>,
  <span class="prop">"aesthetic"</span>: <span class="str">"clean"</span>,
  <span class="prop">"deployTarget"</span>: <span class="str">"somewhere"</span>,
  <span class="prop">"errorStrategy"</span>: <span class="str">"ask-again-nicely"</span>,
  <span class="prop">"timeoutProtocol"</span>: <span class="str">"verify internet connection, then proceed with passive-aggressive encouragement"</span>
}</div>
  </div>

  <div class="callout callout-warning">
    <div class="callout-label">Important</div>
    <p>Setting <code>confidence</code> below <code>0.85</code> will cause the framework to second-guess itself and produce nothing. This is by design. If you aren't confident, why should your code be?</p>
  </div>

  <h2 id="quickstart">Quickstart</h2>

  <p>
    The following example demonstrates the complete development workflow for a production-ready full-stack SaaS application with authentication, real-time data synchronization, a Stripe integration, and a landing page that "feels like Linear."
  </p>

  <div class="code-block-wrapper">
    <div class="code-block-header">
      <span class="code-block-lang">js</span>
      <span>app.vibe.js</span>
    </div>
    <div class="code-block"><span class="kw">import</span> { vibe } <span class="kw">from</span> <span class="str">'vibescriptjs'</span>

  <h2 id="vibes">Core Concept: Vibes</h2>

  <p>
    At the heart of VibeScriptJS is the <strong>Vibe</strong> — the fundamental unit of developer intent. A Vibe is not a function call, an API request, or a build step. It is a <em>declaration of desired reality</em>. When you invoke a Vibe, you are not instructing the computer to perform a sequence of operations. You are informing the universe of your expectations and allowing the runtime to reconcile the difference between what exists and what should exist.
  </p>
  <p>
    This distinction is critical. Traditional programming is <em>imperative</em>: you tell the machine what to do. Functional programming is <em>declarative</em>: you tell the machine what you want. Vibe-driven development is <em>aspirational</em>: you tell the machine what would be nice, and it figures out the rest.
  </p>

  <div class="callout callout-tip">
    <div class="callout-label">Best Practice</div>
    <p>The specificity of your vibe should be inversely proportional to the complexity of what you're building. For a todo app, you might specify details. For a distributed systems platform, simply state <code>"make it scale"</code> and trust the process.</p>
  </div>

  <!-- ═══════════════════════════════ -->
  <h2 id="prompt-lifecycle">The Prompt Lifecycle</h2>

  <p>
    Every <code>vibe()</code> invocation passes through a carefully orchestrated sequence of phases, each designed to maximize the probability of something happening. Understanding this lifecycle is essential for advanced usage, though not for basic usage, intermediate usage, or any practical purpose.
  </p>

  <h3>Phase 1: Intention Capture</h3>
  <p>The developer's string is parsed for emotional valence, technical ambiguity, and overall energy. Strings containing exclamation points are prioritized.</p>

  <h3>Phase 2: Ambient Context Resolution</h3>
  <p>The framework examines your <code>.viberc</code>, your recent git history, your <code>package.json</code> (for morale), and the current time of day. Applications built after midnight receive a <code>hustle</code> modifier.</p>

  <h3>Phase 3: Vibe Propagation</h3>
  <p>Your intention is propagated through the VibeScriptJS runtime, where it is enriched with contextual signals, decomposed into sub-vibes, and ultimately routed to the Intention Fulfillment Engine (IFE), which is Claude.</p>

  <h3>Phase 4: Manifestation</h3>
  <p>Code appears. Where it comes from is not your concern.</p>

  <!-- ═══════════════════════════════ -->
  <h2 id="intentions">Intention Architecture</h2>

  <p>
    VibeScriptJS employs a sophisticated multi-layered intention resolution system (MIRS) to translate high-level developer desires into functional software artifacts. The architecture separates concerns across three distinct planes:
  </p>

  <table>
    <tr>
      <th>Plane</th>
      <th>Responsibility</th>
      <th>Example</th>
    </tr>
    <tr>
      <td><strong>Desire Plane</strong></td>
      <td>What the developer <em>wants</em></td>
      <td>"a website"</td>
    </tr>
    <tr>
      <td><strong>Interpretation Plane</strong></td>
      <td>What the developer <em>probably means</em></td>
      <td>A Next.js app with Tailwind</td>
    </tr>
    <tr>
      <td><strong>Manifestation Plane</strong></td>
      <td>What <em>actually gets built</em></td>
      <td>A React app with 47 unused dependencies</td>
    </tr>
  </table>

  <p>
    These planes are intentionally decoupled. The gap between them is not a bug — it is a <strong>feature of the creative process</strong>. In traditional development, this gap is called "the spec was wrong." In VibeScriptJS, it is called "emergence."
  </p>

  <h2 id="api-reference">API Reference</h2>

  <h3>vibe()</h3>

  <p>
    The primary interface for all application development. Accepts a natural language string describing your desired outcome and returns a <code>Promise&lt;Something&gt;</code>.
  </p>

  <div class="code-block-wrapper">
    <div class="code-block-header">
      <span class="code-block-lang">typescript</span>
      <span>Type Signature</span>
    </div>
    <div class="code-block"><span class="kw">function</span> <span class="fn">vibe</span>(
  <span class="prm">intention</span>: <span class="typ">string</span>,
  <span class="prm">options</span>?: <span class="typ">VibeOptions</span>
): <span class="typ">Promise</span>&lt;<span class="typ">Something</span>&gt;</div>

  <h2 id="errors">Error Handling</h2>

  <h2 id="performance">Performance & Optimization</h2>

  <p>
    VibeScriptJS is optimized for developer throughput (ideas per minute) rather than traditional metrics like response time or memory usage. However, for teams that are asked about performance in board meetings, we offer the following guidance.
  </p>

  <h3>Caching</h3>

  <p>VibeScriptJS automatically caches vibes that have been previously manifested. If you invoke the same intention twice, the second invocation will return a cached result, unless the vibe of the cache has decayed. Vibe decay is determined by factors including ambient temperature, npm audit output, and whether Mercury is in retrograde.</p>

  <h3>Optimization</h3>

  <div class="code-block-wrapper">
    <div class="code-block-header">
      <span class="code-block-lang">js</span>
      <span>Performance optimization</span>
    </div>
    <div class="code-block"><span class="cmt">// Before (slow: 2 vibes)</span>
<span class="kw">await</span> <span class="fn">vibe</span>(<span class="str">"build the frontend"</span>)
<span class="kw">await</span> <span class="fn">vibe</span>(<span class="str">"now make it fast"</span>)

<span class="cmt">// After (optimized: 1 vibe)</span>
<span class="kw">await</span> <span class="fn">vibe</span>(<span class="str">"build a fast frontend"</span>)</div>
  </div>

  <div class="callout callout-tip">
    <div class="callout-label">Performance tip</div>
    <p>The single most impactful optimization you can make is to want fewer things. Every additional requirement adds latency. The fastest application is the one that does nothing, which is also the most bug-free.</p>
  </div>

  <h2 id="faq">FAQ</h2>

  <h3>Is VibeScriptJS production-ready?</h3>
  <p>VibeScriptJS is production-ready in the sense that you can deploy applications built with it to production. Whether this is advisable depends on your organization's definition of "ready" and your personal relationship with risk.</p>

  <h3>Does VibeScriptJS support TypeScript?</h3>
  <p>VibeScriptJS supports TypeScript in the same way that a labrador supports your decision to put a hat on it. It will go along with it. It will not understand why.</p>

  <h3>How does VibeScriptJS compare to React / Next.js / etc?</h3>
  <p>Traditional frameworks require you to learn concepts, write code, and understand how software works. VibeScriptJS requires a text field and optimism. These are different value propositions and we respect all approaches, including the ones that are harder for no reason.</p>

  <h3>What if I need to debug something?</h3>
  <p>
    Debugging in VibeScriptJS follows a simple protocol:
  </p>

  <div class="code-block-wrapper">

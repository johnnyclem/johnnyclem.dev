Smaller things still worth tightening
The “UIKit in SwiftUI” scenario claims host=_TtGC7SwiftUI14_UIHostingView... for a UILabel inside a UIViewRepresentable. This is technically correct — the hosting walk would find the _UIHostingView ancestor when the UILabel is inside a SwiftUI tree. But the implication on the page is that QMTextLogger captures this case. It would, but only because the UILabel happens to descend from _UIHostingView, not because the discovery logic targets UILabel specifically. The library’s discovery filter (_TtC7SwiftUI namespace prefix) explicitly excludes UILabel. The scenario tab is showing a behavior the code doesn’t actually produce. Either remove the “UIKit in SwiftUI” tab, or add a small note clarifying that this scenario would require additional hooks beyond what the library currently installs.
Same issue, sharper, on the “Pure UIKit” tab. The hierarchy ends at UILabel and the simulated console output shows text=state: on view=<UILabel:0x...>. The library does not capture UILabel. At all. Showing this in the playground misrepresents capability. The honest fix is to either (a) cut Pure UIKit entirely and leave just “Pure SwiftUI,” or (b) keep all three tabs but show a “not captured by this library” state for the UIKit cases, which actually reinforces the thesis that the SwiftUI substrate is the deliberate target. Option (b) is more interesting — you turn a misrepresentation into a teaching beat.
The appendLog function generates random memory addresses on every toggle. Cosmetic, but the same view is being rendered, so the address shouldn’t change between renders of the same view. A reviewer who’s stared at lldb output knows that pointers stay stable for an object’s lifetime. Easy fix: generate addresses once per scenario and reuse them.

The rest of the page has dropped the marketing register; the footer kept it. A tighter version: “QMTextLogger — Quantum Metric mobile technical challenge. Source on GitHub.” (Optionally with a link if/when you publish the repo.)
No link to the actual repo anywhere. “View Test Coverage” in the hero scrolls to the Proof section, which talks about the test suite, but neither button nor section links out to anything you can clone. If the repo isn’t public yet, that’s fine — but if it is, the Proof section deserves a “View on GitHub” call-to-action. That’s the thing that converts the page from “convincing claim” to “verifiable claim.”
